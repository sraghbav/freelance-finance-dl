# 5. Discussion

## 5.1 What the results show

**The earlier evaluation was the first problem.** The course-project detector appeared to work (98.2% spike recall) because the test measured whether the model could detect inputs that real data cannot produce. Once anomalies were injected the way an unusual charge would appear, the same detector was at chance. Two flaws compounded: scaling each window independently threw away absolute size, and the test never asked about size at all. A second flaw of the same kind was found later: windows that mixed income and expenses, and almost no income windows, meant the system had never really been tested on half of what the thesis claims to cover. A detector evaluated on an invalid test can look good for reasons unrelated to its purpose, and the corrected pipeline's lower numbers are more informative than the earlier high ones.

**How an amount is scaled matters more than which model scores it.** With min-max scaling every detector was at chance on BudgetWise. Scaling relative to the user's typical amount made detection possible. Scaling by how much each history normally varies was the largest effect found: on real bank expenses a one-line rule caught 43 ± 1% of 50% changes with variability-aware scaling and 5% to 7% with log-ratio scaling, and in the simulation a 50% rise in rent went from 0% to 100% detected with no false alarms. The reason is simple: a 50% change in a payment that never varies is enormous, and the same change in a grocery bill is ordinary, so one threshold for both fails unless each amount is judged against its own history's variability. Real accounts contain both kinds of history (half of the Berka windows come from histories at the variability floor), and BudgetWise, where every category is equally random, hid the problem.

**A deep model was not needed for this task.** On all three datasets a one-line rule computed from the same features matched or beat the autoencoder: tenfold spikes on BudgetWise (73.6 ± 4.1% against 41.0 ± 3.7%); every factor on real bank expenses (for example 43 ± 1% against 14 ± 6% at ×1.5, and 62 ± 2% against 51 ± 7% at ×10); and average precision at every habit level of the simulation (0.77, 0.69, 0.43, 0.33 against 0.70, 0.38, 0.27, 0.23 for the best autoencoder). The direction-aware rules use knowledge a deployed detector lacks, so those comparisons are not entirely fair to the autoencoder, but the direction-unknown rule already won on Berka expenses and in the simulation, and the autoencoder never exceeded the best rule. Larger bottlenecks and variability-aware features helped the autoencoder, but not enough.

**Why: habits are in the scaling, and the data have no sequence dependence.** The structure these datasets do have, a persistent level per user and category and a characteristic variability, is exactly what the scaling captures, and the rules use it too. What an LSTM could add is structure across the five positions, and there is none to find in BudgetWise (autocorrelation about −0.07) or in the real Berka data (0.013 for expenses, −0.054 for income), where amounts are nearly constant or independent from one transaction to the next. The simulation tested this directly: it contains seasonal cycles and repeated amounts, and neither the autoencoder nor any other detector found those anomalies (AUROC 0.29 to 0.62). So the autoencoder did not learn the sequence structure even when it was there. This is a statement about this model, windows of five amounts, and the amount of training I gave it; I did not try longer windows, dates as inputs, or a forecasting objective. It is not a claim that sequence models cannot help on data with real temporal habits.

**Income is dataset-dependent.** For unexpectedly low income, a rule caught 94.7% of tenfold drops on BudgetWise but no method did better than 19% on Berka. For high income, direction-aware rules did well on both (73% to 94% at ×10 on Berka, against 34% for the autoencoder). On Berka the direction-unknown rule was at chance for income, because income histories are heavy-tailed, so many ordinary windows already contain a very large deviation and the threshold becomes very high. A plausible reason for the BudgetWise result is that its income has a floor near 10,000, so a large drop leaves the normal range; I did not test this. The practical point is that a missed or shrunken payment, the case that matters most for a freelancer's cash flow and tax set-aside, was not reliably detectable on the real bank data by any method here.

**Sensitivity of the autoencoder.** The autoencoder's scores depended on how very large inputs were compressed (an earlier clipped version of the variability-aware features gave it higher scores on the simulation than the arcsinh version used here) and on the habit level, whereas the rules' rankings did not. Any claim about the autoencoder in this thesis therefore holds for the configurations tested.

## 5.2 What the grounding check does and cannot do

The check removed the failures that are easy to define mechanically: placeholders, currency symbols, a wrong direction, an invented data-entry error, numbers that do not appear in the facts, and (after round v5) income described as spending. It never rejected a text the judge considered fully correct. It cannot detect a true number used for the wrong purpose, which was the main failure in round v2 ("the threshold of 1.06" for a severity ratio), nor a cause invented in words it does not look for ("may have made a mistake when entering the amount" in round v7). Two lessons follow. First, giving the model less is a stronger defense than filtering what it says: hiding the three fields it misused removed that failure class completely. Second, a filter that checks values does not check meaning; a stronger design would have the model produce a structured statement ("amount X is Y times typical") that can be verified directly instead of free text. The round-v5 failure also shows a limit of any check written after the fact: income described as spending was only noticed by reading the outputs, and then added as a rule.

The general design, computing facts in code, letting a model only phrase them, verifying the result, and falling back to a template, is useful because it bounds the damage of any single failure: the worst case is the template text. The design does not depend on the detector, since it needs only a window and the position of the unusual amount; but I evaluated it only on the autoencoder's flags on BudgetWise, not on the flags of a rule-based detector or on Berka.

## 5.3 Template versus language model

In the final round the language model's output was fully correct for 95% of 20 windows against 100% for the template, with heavily overlapping intervals, so within this evaluation the model added phrasing variety and not accuracy. The model is also brittle: one prompt rewrite (round v6) made it write a currency symbol in 16 of 20 texts, and a second rewrite restored it, so results depend on exact wording and would need re-checking after any change. The final texts also pass partly by saying less (they usually omit how large the difference is), which the rubric does not penalize. Whether the variety helps a reader was not tested, and no user study was done. The model is only 3 billion parameters; a larger one, which could not be tried for lack of budget, might change this.

## 5.4 Limitations

- **Data.** BudgetWise appears synthetic, with no per-user or time structure; many rows were corrupt, duplicated, or unparseable, and the order of 3,713 ambiguous dates is assumed. Berka is real but comes from one bank in the 1990s, in koruna, and I excluded the bank's own interest, fee, and penalty entries (about a third of the rows) by my own judgment. The simulation is synthetic by construction. Nothing here describes how people spend money today.
- **Evaluation design.** For real and BudgetWise data, anomalies are injected: a multiplicative change to a small amount may stay inside the normal range, so recall is bounded well below 100% even for a perfect detector, and the numbers support comparison between detectors, not absolute claims. Thresholds are set by percentile, so the false-positive rate is built in. Only two kinds of change were injected on real data. No real data here contain labeled unexpected expenses or income.
- **Circularity of the simulation.** I designed the habits and the anomalies, so the simulation shows what is possible given such structure; its conclusions about the rules and the autoencoder are conditional on my design.
- **Statistics.** Five folds make the standard deviations rough (some Berka standard deviations are large, for example ±15 points for drops); on Berka, injected anomalies were applied to a sample of 3,000 windows per stream per fold and the autoencoder was trained on 40,000 windows, not all of them; the simulation has three seeds; income on BudgetWise has about 300 windows per fold; each explanation round has 20 windows.
- **Scaling.** The typical amount and the variability use each history's whole data, including later and held-out data. A deployed detector would only know the past.
- **Single feature and short windows.** Only the amount, in windows of five, is used: no dates, transaction type beyond income and expense, or merchant.
- **Judge and checker.** Explanation scores come from Claude, which also wrote the prompts and the checker; a 12-text human check on one round agreed on 81% of judgments (58% for plain language). The scoring is weakly blind. The checker misses meaning errors.
- **Overlapping windows.** One unusual transaction produces several flagged windows; 55% of the primary model's flags on BudgetWise are rent windows, an artifact of rent's wide distribution.
- **Tax module.** A flat 25% placeholder, not evaluated, with no jurisdiction-specific rules.
- **Model size.** Only one small local language model was tested, and it was sensitive to prompt wording.

## 5.5 Ethics and responsible use

The system is an educational prototype, and every tax-related output carries a disclaimer: it is not financial or tax advice, and a wrong set-aside number could lead a real freelancer to under-save. A missed income shortfall, which the results show is hard to detect on real data, could give false reassurance. Using a local model keeps data on the user's machine in the explanation layer. The Berka data are real but anonymized and public; BudgetWise and the simulation contain no real people. The system flags and explains but never acts, so a person stays in the loop. The use of generative AI in building, evaluating, and drafting this work was substantial and is disclosed in Appendix A; the development process sent code and excerpts of the datasets to an external service even though the explanation model ran locally. Claude both wrote parts of the system and scored its outputs, which is why a human agreement check was done and why the results should be read with that in mind.

## 5.6 Future work

- Replace the autoencoder with a variability-aware rule as the detector in the end-to-end pipeline, run the explanation evaluation on it, and extend the evaluation to the Berka data.
- Test whether a sequence model helps with inputs that carry structure the amounts alone do not: dates and day of month, longer windows, a forecasting objective, and per-category models, using labeled anomalies in real data if they can be obtained.
- Examine income more closely: separate income sources, recurring pay, and missed or late payments, with more windows per fold and a way to handle heavy-tailed income histories.
- Combine spike and drop scores into one direction-unknown detector that does not assume a direction.
- Replace free-text explanations with structured statements that a checker can verify, add an informativeness criterion to the rubric, test larger models, and run a user study.
- Repeat the human scoring on all rounds with several independent raters.
