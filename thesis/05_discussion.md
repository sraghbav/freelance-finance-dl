# 5. Discussion

## 5.1 What the results show

**The earlier evaluation was the first problem.** The course-project detector appeared to work (98.2% spike recall) because the test measured whether the model could detect inputs that real data cannot produce. Once anomalies were injected the way an unusual charge would appear, the same detector was at chance. Two flaws compounded: scaling each window independently threw away absolute size, and the test never asked about size at all. A detector evaluated on an invalid test can look good for reasons unrelated to its purpose, and the corrected pipeline's lower numbers are more informative than the earlier high ones. A second, smaller flaw of the same kind was found late: windows that mixed income and expenses, and almost no income windows, meant the system had never really been tested on half of what the thesis claims to cover.

**The autoencoder detects large spikes and little else.** With user-relative features and cross-validation, it flags a charge ten times too large about 41% of the time at a 5% false-positive rate, and it is near chance at a factor of 2 or below and weak for drops. In practice it can notice a charge that is far out of range for that user and category, not subtler deviations.

**On both datasets, a simple rule does at least as well.** On BudgetWise, a one-line rule that knows the anomaly is a spike reaches 73.6% against the autoencoder's 41.0% at ×10, and a rule that knows it is a drop matches the better autoencoder. On the Sparkov data with real fraud labels, the best autoencoder (latent size 16) ties the best rule on average precision (0.070) but is lower on AUROC (0.708 against 0.732) and on the share of fraud caught (28.5% against 37.2%), and the latent-3 autoencoder is clearly worse and does not improve with four times more training data. The direction-aware rules use knowledge a deployed detector would not have, so this is not entirely fair to the autoencoder, and a fairer comparison would use a combined spike-and-drop score, which I did not build. The conclusion is still that, for a point anomaly in amount, the learned model is not justified on this evidence.

**Why: little for a sequence model to learn (partly tested).** BudgetWise has no persistent per-user level and no time structure (Section 4.6). Sparkov has persistent per-user levels in some categories, but they are already captured by scaling each amount by the user's typical value, which the rules use too, and Sparkov also has no time structure (lag-1 autocorrelation 0.02). A model whose strength is order and personal history is not given order to exploit. This is a statement about these datasets. Real transactions have habits such as recurring rent, subscriptions, and regular pay, and whether an LSTM autoencoder helps on data with such habits was not tested.

**Income, the case that matters for the intended use.** For unexpectedly low income, a one-line rule catches 94.7% of tenfold drops and 59.7% of fivefold drops, while the autoencoder catches 8.3% and 6.9%. This matters because a missed or shrunken payment is the shortfall most relevant to a freelancer's cash flow and to the tax set-aside, and it is the one the learned model handles worst. A plausible reason (not tested) is that income has a floor near 10,000, so a large drop leaves the normal range, and the rule uses that directly, while the autoencoder was trained mostly on expense windows (82% of the training windows) where small amounts are common. Unexpectedly high income is hard for every method, perhaps because high income payments are already common in this data (4.6% exceed 100,000). Income has far fewer windows (about 300 per fold), so these results are noisier.

**Why the autoencoder beats the direction-unknown rule on spikes (hypothesis, not tested).** Training data contain few large positive deviations from the typical amount (non-rent amounts are bounded near 10,000) and many large negative ones (small amounts are common). A model that has learned this asymmetry reconstructs large positive values badly and large negative ones well, making it good at spikes and poor at drops, as observed. A rule on the absolute value cannot represent the asymmetry.

## 5.2 What the grounding check does and cannot do

The check removed the failures that are easy to define mechanically: placeholders, currency symbols, a wrong direction, an invented data-entry error, numbers that do not appear in the facts, and (after round v5) income described as spending. It never rejected a text the judge considered fully correct. It cannot detect a true number used for the wrong purpose, which was the main failure in round v2 ("the threshold of 1.06" for a severity ratio), nor a cause invented in words it does not look for ("may have made a mistake when entering the amount" in round v7). Two lessons follow. First, giving the model less is a stronger defense than filtering what it says: hiding the three fields it misused removed that failure class completely. Second, a filter that checks values does not check meaning; a stronger design would have the model produce a structured statement ("amount X is Y times typical") that can be verified directly instead of free text. The round-v5 failure also shows a limit of any check written after the fact: income described as spending was only noticed by reading the outputs, and then added as a rule.

The general design, computing facts in code, letting a model only phrase them, verifying the result, and falling back to a template, is useful because it bounds the damage of any single failure: the worst case is the template text.

## 5.3 Template versus language model

In the final round the language model's output was fully correct for 95% of 20 windows against 100% for the template, with heavily overlapping intervals, so within this evaluation the model added phrasing variety and not accuracy. The model is also brittle: one prompt rewrite (round v6) made it write a currency symbol in 16 of 20 texts, and a second rewrite restored it, so results depend on exact wording and would need re-checking after any change. The final texts also pass partly by saying less (they usually omit how large the difference is), which the rubric does not penalize. Whether the variety helps a reader was not tested, and no user study was done. The model is only 3 billion parameters; a larger one, which could not be tried for lack of budget, might change this.

## 5.4 Limitations

- **Data.** Both datasets are synthetic. BudgetWise is in rupees, with no per-user or time structure and an unusual rent distribution; many rows were corrupt, duplicated, or unparseable, and the order of 3,713 ambiguous dates is assumed. Nothing here describes real spending.
- **Evaluation design.** Injected multiplicative anomalies are not necessarily unusual in absolute terms, so recall is bounded well below 100% even for a perfect detector, and the numbers support comparison rather than absolute claims. Thresholds are set by percentile, so the false-positive rate is built in. Only two kinds of anomaly were injected. The Sparkov test uses only the amount, while real fraud depends on category, time, and place.
- **Statistics.** Five folds make the standard deviations rough; income has about 300 windows per fold; each explanation round has 20 windows.
- **Scaling.** The typical amount uses each user's whole history, including later and validation data.
- **Income.** All income sources are pooled into one stream per user, and the data contain no recurring-income pattern, so whether habits in real income help detection is untested.
- **Judge and checker.** Explanation scores come from Claude, which also wrote the prompts and the checker; a 12-text human check on one round agreed on 81% of judgments (58% for plain language). The scoring is weakly blind. The checker misses meaning errors.
- **Overlapping windows.** One unusual transaction produces several flagged windows; 55% of flags are rent windows, an artifact of rent's wide distribution.
- **Tax module.** A flat 25% placeholder, not evaluated, with no jurisdiction-specific rules.
- **Model size.** Only one small local language model was tested, and it was sensitive to prompt wording.

## 5.5 Ethics and responsible use

The system is an educational prototype, and every tax-related output carries a disclaimer: it is not financial or tax advice, and a wrong set-aside number could lead a real freelancer to under-save. Using a local model keeps data on the user's machine in the explanation layer, and no real personal data were processed, because both datasets are simulated or synthetic-looking (the Sparkov file contains invented names and addresses). The system flags and explains but never acts, so a person stays in the loop. The use of generative AI in building, evaluating, and drafting this work was substantial and is disclosed in Appendix A; the development process sent code and excerpts of the datasets to an external service even though the explanation model ran locally. Claude both wrote parts of the system and scored its outputs, which is why a human agreement check was done and why the results should be read with that in mind.

## 5.6 Future work

- Evaluate on real, consented transaction data, or on a simulator whose users have realistic habits (recurring bills, regular pay), so a sequence model has structure to learn; test whether the autoencoder then beats the rules.
- Build and compare a combined detector (separate spike and drop scores), and test models that use dates, merchants, categories, and location, which real fraud depends on.
- Examine income more closely: separate income sources, recurring pay, and missed or late payments, with more windows per fold.
- Replace free-text explanations with structured statements that a checker can verify, add an informativeness criterion to the rubric, test larger models, and run a user study.
- Repeat the human scoring on all rounds with several independent raters.
