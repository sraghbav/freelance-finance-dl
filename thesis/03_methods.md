# 3. Methods

**Overview of the data.** Three datasets are used. The original BudgetWise dataset (Sections 3.1 to 3.9) is where the pipeline was built and the course-project errors were found; its structure is close to random. The Berka bank data (Section 3.11) are real and have strong per-account habits. The simulation (Section 3.12) has habits and labeled anomalies by design, so the effect of structure can be controlled. Section 3.2 defines the three feature types that are compared.

## 3.1 Dataset and data quality

I used the BudgetWise Personal Finance Dataset from Kaggle. It has 15,900 transaction rows for 150 users covering 1 January 2021 to 31 December 2024, with the fields `transaction_id`, `user_id`, `date`, `transaction_type`, `category`, `amount`, `payment_mode`, `location`, and `notes`. The dataset appears to be synthetic (Section 4.5), and the locations (Mumbai, Bangalore, Chennai) and amounts such as `₹5070` and `Rs.828` indicate that amounts are in rupees. I report amounts as plain numbers without a currency.

The raw file is messy, and how it is cleaned changes every later result. Table 3.1 lists the problems found and how each was handled.

**Table 3.1. Data problems and handling.**

| Problem | Evidence in the raw file | Handling |
|---|---|---|
| Category spellings | 46 distinct strings (for example `FOOD`, `Fod`, `Foods`) | Lowercased and mapped by a lookup table to 13 canonical categories |
| Mixed date formats | `2023-04-25` (6,091 rows), `08/05/2022` (4,676), `31-12-23` (3,044), `21-09-2024` (1,603); 486 rows have no date | Each format parsed with its own rule (below) |
| Amounts with currency text | 2,377 amounts such as `₹5070`, `Rs.828`, `5107 INR`; 291 amounts missing | Currency text and commas stripped before parsing |
| Missing required fields | 285 categories, 291 amounts, 486 dates, 0 user ids; 1,004 rows missing at least one required field (45 income rows with a missing category are kept, because pooled income needs no category) | Rows dropped |
| Duplicates | 843 rows identical in transaction id, user, date, type, category, and amount | Removed |
| Shared transaction ids | 890 rows share an id with a different transaction | Kept |
| Corrupt amounts | 373 rows: 75 equal to 999,999,999, 83 equal to 999,999, 72 equal to zero, 143 negative | Dropped in the primary pipeline |

**Dates.** The four formats are each internally consistent. Slash dates are always month/day/year: none has a first field above 12, and 2,811 have a second field above 12. Dash dates are always day-month: none has a second field above 12, while 1,846 of the 3,044 two-digit-year dates and 953 of the 1,603 four-digit-year dates have a first field above 12. This is the evidence for the parsing rules. It cannot settle every row: 3,713 dates (1,865 slash, 1,198 two-digit dash, 650 four-digit dash) have both fields at or below 12, so their order is assumed from the rest of their format. A misread day and month would only shift a transaction by up to several months within the same user and category, but it can change the order of transactions within a window, so I treat the ordering of a few windows as uncertain.

**Row loss in the original loader.** The loader written for the course project parsed only ISO dates and plain numbers, and silently dropped everything else. It kept 4,977 of 15,900 rows (31.3%) and produced 1,104 windows. After parsing every format and stripping currency text, 14,896 rows have all required fields; removing 843 duplicates leaves 14,053 rows (88.4%); dropping the 373 corrupt amounts leaves **13,680 rows** (86.0%) (Figure 4.1). I fixed the loader instead of only reporting the loss because every downstream quantity, including which users and categories appear at all, depends on it.

**Corrupt amounts.** I dropped the 373 rows instead of repairing them, because there is no basis for imputing a value: `999999` and `999999999` look like placeholders, and zero or negative amounts could be refunds or errors. Dropping removes any genuine refunds. `[YOUR CALL: say whether you agree with this tradeoff.]` Because each transaction lies in up to five overlapping windows, these 373 rows (2.7% of rows) touched 1,133 of 8,882 windows (12.8%) before they were dropped. The legacy pipeline is still available through `--legacy-parsing`; the corrupt-amount filter is the `--clean` option and is used in the primary configuration.

**What remains.** After cleaning, the data is dominated by a few categories: food, rent, and travel account for 61% of the windows and pooled income for 18% (Table 3.2). Section 4.5 shows that the amounts also lack per-user and time structure.

## 3.2 Sequences and features

**Windows.** Transactions are grouped by `(user_id, transaction_type, category)` and sorted by date. A window of five consecutive transactions, advanced one step at a time, is one window; groups with fewer than five transactions produce none. Consecutive windows therefore share four of their five values. Because the intended use covers unexpected income as well as expenses (Section 1.3), all of a user's income, from every source, is pooled into one history named "income". Without pooling, income is split across five categories with about three transactions per user each, so almost no window forms: the first version of this pipeline had only 144 income windows (2%). That first version also grouped by user and category alone, which put the income and the expense rows of the category "other" in one history (108 of its 140 windows mixed the two). After cleaning there are **8,537 windows** from all 150 users: 7,000 expense and 1,537 income (Table 3.2). The tax module still uses the original category of each income row (`source_category`). The old grouping is kept as `--legacy-grouping`, and checkpoints trained with it reload with it.

**Features.** Each amount *a* in a window is replaced by log(*a* / *s*), where *s* is the median of that user's valid amounts in that history (that category, or all income) over their whole history. A value of 0 means the user's typical amount, +1.1 means about three times typical, and −1.1 about a third. Ratios are clipped to [0.001, 1000] before the logarithm so that extreme values stay finite. The class project instead scaled each window independently to [0, 1] (min-max scaling), which discards absolute size: a window of 100 to 500 and a window of 10,000 to 50,000 become identical. Min-max scaling is kept as a comparison (`--features minmax`).

**Variability-aware features.** The log-ratio treats a 50% change in a rent payment that never varies and in a grocery bill that swings by a third as equally unusual. The variability-aware ("robustz") feature divides the log-ratio by the history's own typical variability: for each history (a user's expenses in one category, or all of a user's income), the spread is 1.4826 times the median absolute deviation of its log-ratios, with a floor of 0.05, and the feature is arcsinh(log-ratio / spread). An amount is then measured in units of how much that history normally varies. The arcsinh compresses very large values smoothly and preserves the ranking of every score. An earlier version clipped the value at ±20 instead; on the Berka data this saturated 19.8% of income windows, so the 95th percentile threshold of a rule equalled the clip and the rule could never exceed it. I replaced the clip and re-ran every result that uses these features, so all reported results use the arcsinh version.

The typical amount *s* uses each user's entire history, including transactions after the window and, for validation users, transactions the model never trains on. No anomaly labels are involved, but it is a mild look-ahead that a deployed system would not have. In the injection experiments (Section 3.6) *s* is held at its original value, so an injected anomaly does not change its own baseline.

## 3.3 Model and training

The model is an LSTM sequence autoencoder. The encoder is a one-layer LSTM (hidden size 64) over the five values; its final hidden state is projected by a linear layer to a latent vector of size 3. The decoder projects the latent vector back to size 64, repeats it at each of the five positions, passes it through a second one-layer LSTM (hidden size 64), and a linear layer outputs one value per position. The model has 50,948 parameters at latent size 3 (52,625 at size 16).

The latent size is chosen to be smaller than the five inputs. With a size of 16 the network has room to copy the input, and in practice it does: its validation error is 0.0004, against 0.144 at size 3 (Section 4.5). Training minimizes mean squared error with the Adam optimizer (learning rate 0.001, batch size 64) for 50 epochs with random seed 42, on CPU. The saved checkpoint is the epoch with the lowest validation error, which is epoch 45 for the primary model and epoch 39 for the latent-16 ablation.

## 3.4 User-level train and validation split

Because consecutive windows share four of five values, splitting windows at random would put near-copies of the same data on both sides and flatter the validation error. I split by user instead: the 150 users are shuffled with seed 42, the first 22 (15%) are validation users, and the other 128 are training users, giving 7,289 training and 1,248 validation windows. All of a user's windows go to the same side.

## 3.5 Scores and threshold

A window's score is its reconstruction error: the mean over the five positions of the squared difference between input and output. I also tested the maximum over the five positions instead of the mean (Section 4.3). A window is flagged when its score exceeds a threshold, set to the 95th percentile of the scores of the held-out (validation) windows. By construction about 5% of validation windows are flagged, so the false-positive rate is fixed at about 5% and says nothing about how many real anomalies exist. Over all 8,537 windows, 383 (4.5%) are flagged.

In the single-split analysis the same 22 validation users select the checkpoint epoch, set the threshold, and supply the injected-anomaly test. This is mildly optimistic, and it is one reason the cross-validation below matters.

## 3.6 Anomaly evaluation

**Why the original method was invalid.** The course project tested the detector by overwriting one normalized value with 2.0 or −0.5. Normalized inputs always lie between 0 and 1, so these values could never occur in real data, and detecting them shows only that the model can detect impossible inputs.

**Raw-space injection.** In the corrected evaluation, one raw amount in a window is multiplied (spike) or divided (drop) by a factor of 1.5, 2, 3, 5, or 10. The altered window is then converted to features exactly like any other, with the same baseline *s*, scored, and compared with the threshold. The altered position is chosen uniformly at random once per window (seed 42) and reused across factors. I report recall (the share of altered windows flagged) at the threshold above. Chance level is the false-positive rate, about 5%: a detector that ignores the anomaly would flag about as many altered windows as clean ones. This design has a limitation. A multiplicative change to a small amount is not necessarily unusual in absolute terms (turning 200 into 2,000 stays inside the range of normal amounts for most categories), so 100% recall is unattainable even for a perfect detector. Recall values should therefore be used to compare detectors, not as absolute detection rates.

**Cross-validation.** A single split of 22 users is a noisy basis for a claim. I therefore used five-fold cross-validation over users: users are shuffled (seed 42) into five groups of 30; for each fold a fresh model is trained on the other 120 users for 50 epochs (seed 42 plus the fold number), the threshold is the 95th percentile of the held-out windows' scores, and the injection test is run on the held-out windows. Results are reported for all windows and separately for expense windows and income windows (the **streams**); within each stream the threshold is the 95th percentile of that stream's own held-out scores, so each stream has a false-positive rate near 5%. No checkpoint selection is used. I report the mean and standard deviation of recall across the five folds. I also computed Wilson confidence intervals (Wilson, 1927) from the pooled counts, but they treat the 8,537 windows as independent, which they are not (overlapping windows, and several windows per user), so they are too narrow and I do not use them as the main measure of uncertainty. Three configurations were compared: log-ratio features with latent size 3 (primary), log-ratio with latent size 16, and min-max scaling with latent size 3.

**Untrained baselines.** To judge whether the autoencoder adds anything, I scored the same held-out windows and injected the same anomalies with three rules that need no training, all computed from the log-ratio features: the largest absolute value in the window (direction unknown); the largest value (assumes the anomaly is a spike); and the most negative value (assumes it is a drop). Each uses a threshold at the 95th percentile of the clean held-out scores of its stream. The two direction-aware rules use knowledge that a deployed detector would not have, so they show what a one-line rule can reach at best. On the later datasets an Isolation Forest (100 trees; Liu et al., 2008 `[CHECK: citation]`) fitted on the same training windows and features is also included as a standard unsupervised baseline.

## 3.7 Explanation layer

For each flagged window the explanation layer first computes a small set of facts in ordinary code: the position in the window with the largest reconstruction error (the flagged position), the amount there, whether the window is an expense or income, the user's typical amount for that history (the median *s*), the ratio of the two, whether the amount is "higher" or "lower", how many times higher or lower (rounded to one decimal), the median of the other four amounts, any invalid amounts, and the window's score, threshold, and ratio between them. Two texts are then produced from these facts.

1. **Template.** A rule-based sentence with fixed wording that states the position, the amount, how many times higher or lower than typical it is, how far above the threshold the window scored, and that it is an automated flag, not proof of a problem.
2. **Language model.** Llama 3.2 with 3 billion parameters (`llama3.2:3b`), run locally with Ollama at temperature 0 and seed 42. The system prompt (the final version, v7; all versions are in `docs/explanation_eval/prompts.md`) instructs it to use only numbers in the facts and write them with no currency symbol, write two or three plain sentences, say that this is an automated flag and not proof, state the direction from the facts as given without mentioning field names, say "spent" for an expense and "received or earned" for income (never "spent" for income), mention data-entry errors only when the facts say invalid values are present, never invent causes, and give no tax, legal, or investment advice. The user message is the facts as JSON. From the third prompt version on, the model is not shown the score, threshold, or their ratio, because earlier versions mislabeled that ratio.

A leading line such as "Here's an explanation:" is removed before checking. The text is then checked by a **grounding check** that rejects it if any of the following holds: a bracketed placeholder or a field name with an underscore appears; a currency symbol appears; the direction word is missing or the opposite word is present (when no invalid values exist); vocabulary suggesting a data-entry error (such as "data-entry", "placeholder", "negative", "zero", "error") appears when no invalid values exist, or such vocabulary is missing when they do; income is described as spending ("spend", "spent") or the internal ratio field is mentioned; or any number in the text, apart from the digits in the user's id, differs from every number in the facts by more than rounding. If the check fails, the template text is shown instead. The check can verify that a number exists in the facts and that the direction is right. It cannot verify what a number is being used for, or catch an invented claim phrased outside its vocabulary (Section 4.8).

## 3.8 Explanation evaluation

For each evaluation round I drew 20 flagged windows uniformly at random (seed 42) and produced a template text and a language-model text for each. Every text was scored on four binary criteria against the facts: **direction correct** (it says higher or lower correctly); **numbers correct and used correctly** (every number quoted is right and refers to what it should); **plain language** (a non-expert could follow it, with no field names or jargon); and **no invented causes** (it does not assert reasons the data do not support). The text is "fully correct" if it meets all four.

Seven rounds were run. The first (v1) was an informal inspection of five outputs. Round v2 added explicit direction fields and a no-currency rule to the prompt, v3 hid the score fields from the model, and v4 used the v3 prompt on an earlier primary model's flags (before the grouping fix of Section 3.2). Round v5 used the v3 prompt on the final primary model, whose flags include income windows. Round v6 added the transaction type to the facts and an income-wording rule near the start of the prompt, and extended the checker with the income-wording and field-name rules; round v7 rewrote the prompt with the no-currency rule first. Rounds v2 and v3 were run on the same 20 windows, taken from the course-project detector's flags (min-max features, 52 flagged), so they are directly comparable; v4 used a different model's flags and is **not** comparable with them; v5, v6, and v7 use the same 20 windows. Round v6 was not scored by hand, because the checker had already rejected most texts; only its automatic pass rate is reported.

The scoring was done by Claude acting as a language-model judge, for all 40 texts in each round. This is a limitation: Claude also wrote the prompts and the grounding check that are being evaluated, so it is not an independent rater, and the sheets are only weakly blind because the template's wording is formulaic. To measure how far the judge's scores can be trusted, I scored 12 of the 40 texts in round v2 myself (`[CONFIRM: this was done by the author]`) and compared them with the judge's scores. Because of the small number of windows per round, I report 95% Wilson intervals for the rates (Wilson, 1927).

## 3.9 Tax set-aside note

The tax module is an educational placeholder. For a user and calendar quarter, it sums the user's valid freelance-income transactions, sums valid expenses in the categories travel, education, and utilities (treated only as candidate business expenses), takes the difference (not below zero), and multiplies by a flat 25% set-aside rate. Every note carries a disclaimer that it is not tax advice. It was not evaluated, because there is no ground truth, and it applies no jurisdiction's rules.

## 3.11 Real bank data: Berka

The Berka dataset (Berka & Sochorová; released for the PKDD'99 Discovery Challenge) contains real, anonymized transactions of 4,500 accounts of a Czech bank from 1 January 1993 to 30 December 1998, in Czech koruna. I used only its transactions table (1,056,320 rows). Each credit (`PRIJEM`) is an income transaction, and each debit or withdrawal (`VYDAJ`, `VYBER`) is an expense. A transaction's category is its payment-kind symbol where one exists (household payment, insurance, loan payment, pension) and otherwise its operation (cash withdrawal, card withdrawal, transfer out, transfer in, cash deposit). I excluded the bank's own entries, which are not user behavior: interest credited (183,114 rows), statement fees (155,832), and penalty interest (1,577), 340,523 rows in all, leaving 715,797 rows (493,828 expense and 221,969 income). As for the other datasets, each account's income from all sources is pooled into one history. The result is **653,628 windows from all 4,500 accounts**: 256,683 cash withdrawals, 203,969 income, 104,880 household payments, 55,292 transfers out, 16,461 insurance, 10,925 loan payments, and 5,418 card withdrawals. `[CHECK: the source's documentation of the codes, and the exact citation of Berka (2000), Guide to the Financial Data Set.]`

These data have strong per-account habits but no sequence dependence. The share of variance in log-amount explained by account is 0.999 for household payments, 1.000 for insurance and for loan payments, 0.835 for transfers out, 0.447 for cash withdrawals, and 0.511 for pooled income, so standing payments are nearly constant per account. The lag-1 autocorrelation within a history is near zero (0.013 for expenses over 5,017 histories, −0.054 for income over 3,970). Half of the windows (49.2%) belong to histories whose variability is at the floor of 0.05, mostly standing payments, while cash withdrawals are very variable (median spread 0.86).

Evaluation follows the cross-validation of Section 3.6 with a few changes for size: accounts are split into five folds of 900; for each fold the autoencoder is trained on 40,000 randomly chosen training windows for 20 epochs; the threshold is the 95th percentile of the scores of all the held-out windows of the stream; and the injected anomalies are applied to a random sample of 3,000 held-out windows per stream per fold. Compared models are the autoencoder (variability-aware features at latent sizes 3 and 16, and log-ratio features at latent size 16), the three rules, and the Isolation Forest.

## 3.12 Simulation study

Real data cannot show how a detector's usefulness depends on how much structure the data have, so I also generated synthetic data (`habitsim.py`), with documented assumptions and labeled anomalies. For 100 users over three years, each user has either a salaried income (a steady monthly payment) or a freelance income (one to three irregular payments a month), rent that is nearly constant, a fixed subscription, utilities with a yearly cycle, and volatile groceries and dining. Four habit levels vary the structure: **strong** (variability multiplied by 0.5, a yearly utility cycle of ±30%), **default** (variability ×1), **weak** (variability ×2, cycle ±15%), and **none** (every category an independent lognormal draw, identical for all users, with no cycle). With probability 1% per transaction (4% for utilities, so that seasonal anomalies are frequent enough to evaluate) an anomaly replaces the normal amount: a **spike** (multiplied by a factor between 2 and 10), a **drop** (divided by a factor between 2 and 10), a **seasonal** anomaly (a utility bill of the opposite season's size), or a **duplicate** (a grocery or dining amount that repeats the previous one). Each transaction carries a label and an anomaly type, and a window is positive if it contains a labeled anomaly. This is data I designed, so results show what is possible given such structure and not what real data do.

For each habit level and each of three data seeds (1, 2, and 3), users are split 80/20, the autoencoder is trained on 30,000 windows for 15 epochs (latent size 16, with variability-aware and with log-ratio features), and held-out windows are scored by the autoencoder, by the rule that takes the largest absolute feature (with each feature type), and by an Isolation Forest. Scores are judged by AUROC, average precision, and the share of positive windows caught when the 5% highest-scoring windows are flagged, overall, by stream, and by anomaly type, and results are averaged over the three seeds.

A separate per-category test on the simulation uses clean data (default habits, no labeled anomalies, data seed 7, 100 users, one 80/20 user split, latent size 16, 30,000 training windows, 15 epochs) and the injection of Section 3.6 on each category separately with a single threshold shared by all categories, as a deployed detector would use. It isolates the effect of the feature type on categories that differ in how much they vary.
